# project-brain — Design

- **Date:** 2026-10-31
- **Status:** proposed, under review
- **Scope:** MVP
- **Inspired by:** `second-brain` (`sb`) — same "LLM wiki" pattern, rewritten from scratch for a product team

## 1. Goal and context

project-brain (`pb`) is a Claude plugin, usable from **Claude Code** and **Claude Cowork**, that captures the relevant context a product team produces about a software product — functional concepts, features, technical modules and interfaces, decisions, open questions — and stores it **inside the product monorepo** as a typed, linked Markdown wiki optimised for AI agents and readable by humans.

The team is cross-functional: software engineers, product managers, designers, analysts, QA. The company stack is Jira, Confluence, GitHub and Microsoft Teams.

It follows the **LLM Wiki** pattern: raw inputs (documents, threads, pages, PRs, sessions) are ingested by the LLM, which categorises them, links them and keeps a structured wiki up to date. The wiki structure has explicit semantics, defined at initialisation through a grill-style interview and evolved over time.

**Success criterion:** an agent (or a person) working on any part of the product can get, from `brain/`, the functional and technical context it needs — without anyone maintaining the structure by hand — and that context keeps flowing in from where the team already talks (Teams) and writes (Confluence, GitHub).

### Decisions

| Topic | Decision |
|---|---|
| Origin | Rewrite from scratch, keeping second-brain's principles |
| Product scope | One product, one monorepo, one `brain/` |
| Storage | `brain/` at the monorepo root; it is the source of truth |
| Access — devs | **Repo mode**: work on the monorepo; wiki changes are committed on the **current branch** and ride in the same PR as the code |
| Routine writes | Committed and pushed **directly, without a PR**, to a target branch chosen by whoever sets up the routine |
| Access — non-devs | **Read mode**: read-only from Cowork via the official GitHub connector. Their knowledge enters through Confluence and Teams, ingested by the routine |
| Merge policy | Dev PRs follow the monorepo's normal flow, with `pb validate` as a required check on `brain/` changes; PRs touching only `brain/` are auto-merged once it passes |
| Generated files | Regenerated by a GitHub Action after merge to `main`, never inside PRs |
| Schema | Base preset "software product", refined by a **grill-style interview** at `/pb:init` |
| Language | Everything in English; glossary terms bilingual (EN/IT) |
| Raw content | No raw for Teams/meetings (synthesis + permalink). Uploaded files: extracted text only; binaries stay external |
| People | No `person` pages, no names in decisions |
| Tasks | Not in the wiki; Jira is the source of truth |
| Conflicts | Wiki wins on decisions/concepts/modules/interfaces; external sources win on requirement detail; contradictions always become an `open-question` |
| Periodic ingestion | Nightly Claude Code cloud routine created by the Engineering Manager: Teams channels + Confluence spaces + Jira epics + merged PRs |
| Epics | Dedicated `epic` type next to `feature`: the epic page collects what was agreed around a Jira epic in progress; lasting content goes on features/decisions; closed and consolidated when the Jira epic is done |
| Toolkit | Python 3.9+, standard library only, under `scripts/` |
| Distribution | Marketplace in a company GitHub org repo, synced by the org admin into Cowork |
| Session capture | Manual skill `/pb:capture`, triggered by the dev on the current session; no hooks in the MVP |
| Corrections | Dedicated skill `/pb:fix`; decisions are superseded, never rewritten; corrections logged |
| Size control | Significance gate on every write, update-before-create, per-type word budgets checked by the toolkit, lint for duplicates and bloat |

## 2. Architecture

### Principle

**LLM for semantics, toolkit for mechanics.** The LLM understands, classifies, synthesises, links and proposes. The toolkit validates, indexes, resolves names, builds generated files, tracks sync cursors and applies migrations. The toolkit never calls the LLM; the LLM never does by hand what the toolkit does.

### Plugin repo (`project-brain`, no content)

```
project-brain/
├── .claude-plugin/
│   ├── plugin.json              # name: "pb"
│   └── marketplace.json
├── skills/
│   ├── init/  put/  meeting/  capture/  sync/
│   ├── ask/   context/  lint/  schema/  routine-setup/
│   └── _shared/                 # conventions, ingestion pipeline, mode detection
├── scripts/
│   ├── pb.py                    # deterministic CLI (entry point)
│   └── pb_core/                 # frontmatter, validate, index, glossary, context, resolve, state, secrets…
├── presets/
│   └── software-product/        # base schema the init interview starts from
├── templates/
│   ├── brain/                   # AGENTS.md, README skeleton
│   ├── github/                  # workflows: pb-validate.yml, pb-generate.yml
│   └── routine/                 # nightly routine prompt template
├── docs/specs/
└── tests/
```

No `bin/` directory (it blocks Cowork and org distribution). Skills invoke `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pb.py" …`.

### The wiki inside the monorepo

```
<monorepo>/
├── CLAUDE.md                    # gets a pointer: "for product context read brain/AGENTS.md"
├── .github/workflows/
│   ├── pb-validate.yml          # on PR touching brain/: pb validate
│   └── pb-generate.yml          # on push to main touching brain/: regenerate, commit
└── brain/
    ├── AGENTS.md                # how agents should read and write the brain
    ├── schema/
    │   ├── VERSION
    │   ├── brain.md             # product name, language for glossary, thresholds
    │   ├── types/<type>.md      # one file per type (frontmatter for toolkit, prose for LLM)
    │   ├── sources.md           # configured Teams channels, Confluence spaces, Jira projects
    │   └── proposals.md         # schema evolution proposals
    ├── functional/
    │   ├── features/
    │   └── concepts/
    ├── technical/
    │   ├── modules/
    │   ├── interfaces/
    │   └── environments/
    ├── epics/                   # Jira epics in progress: agreed scope, constraints, discussion
    ├── decisions/
    ├── open-questions/
    ├── digests/                 # one per routine run: what was ingested/skipped and why
    ├── raw/YYYY/MM/             # extracted text of uploaded files, immutable
    ├── context/                 # GENERATED: context packs per feature and per active epic
    ├── index.md                 # GENERATED: one line per page
    ├── glossary.md              # GENERATED: from concepts, bilingual
    └── .pb/
        ├── backlinks.json       # GENERATED
        └── state/               # sync cursors (teams.json, confluence.json, github.json)
```

`schema/types/*.md` follow second-brain's convention: YAML frontmatter (restricted subset) read by the toolkit, prose read by the LLM (when to create, how to structure the body, what to exclude).

### Modes

The plugin detects its mode at the start of every skill:

| Mode | Detection | Who | Capabilities |
|---|---|---|---|
| **Repo mode** | `brain/schema/VERSION` found walking up from cwd | Developers (Claude Code) | All skills; read + write; toolkit available |
| **Read mode** | No local brain; GitHub connector available | Non-devs (Cowork) | `ask`, `context` only; reads `brain/` from `main` via the connector |

In read mode, write skills explain that knowledge enters through Teams and Confluence and that a developer can run `/pb:put`. Read mode does not require Python: it only reads files (`index.md` first, then linked pages, `glossary.md`, `context/`).

### Write flow (repo mode)

1. LLM semantic work (classify, synthesise, link, detect contradictions).
2. Page writes.
3. `pb validate` — fix and repeat until clean.
4. `git commit` of the `brain/` changes only, on the **current branch** (message `pb(<skill>): …`). No push: changes travel with the developer's PR. If the current branch is the default branch, the skill warns and asks before committing.

The routine has its own flow, described in §6.

Generated files (`index.md`, `glossary.md`, `context/`, `.pb/backlinks.json`) are **not** written in PRs. Locally the toolkit can regenerate them in a gitignored cache so `ask`/`context` work offline, but only `pb-generate.yml` commits them on `main`. This avoids merge conflicts between parallel PRs.

### CI

`pb scaffold` vendors the toolkit into `brain/.pb/toolkit/` (with its version), so workflows run `python3 brain/.pb/toolkit/pb.py …` without access to the plugin repo; `pb toolkit-sync` refreshes it after a plugin upgrade.

- **`pb-validate.yml`** — on PRs touching `brain/`: runs `pb validate` (schema, links, required fields, title uniqueness, secret patterns). Required check.
- **Auto-merge** — branch rule/ruleset: a PR whose diff is entirely under `brain/` and whose `pb validate` passes is auto-merged (no human review), including schema changes and deletions.
- **`pb-generate.yml`** — on push to `main` touching `brain/`: `pb generate` (index, glossary, context packs, backlinks) and commits the result. Routine commits reach `main` either directly (if the routine targets `main`) or when its target branch is merged.

## 3. Content model

### 3.1 Areas

The brain is split into a **functional** knowledge base and a **technical** one, plus cross-cutting **epics**, **decisions** and **open questions**.

- **functional** — what the product is and does: domain concepts (the glossary), features, functional and UX choices.
- **technical** — how it is built: modules of the monorepo, interfaces between them and with the outside, environments.
- **cross-cutting** — epics in progress (Jira epics and what was agreed around them), decisions (functional, UX or technical) and open questions that block them.

Knowledge pages are **updated and consolidated** (stable sections, no fine-grained chronology). Epics, decisions and open questions are **created and closed** (they have a lifecycle).

**Propagation rule:** a decision that changes stable knowledge also updates the affected feature/module/interface page and links to it.

### 3.2 Page format

```markdown
---
type: feature
title: Invoice Approval Flow
aliases: [approval flow]
created: 2026-10-31
updated: 2026-10-31
sources: ["jira:FIN-412", "confluence:PROD/123456", "teams:<team>/<channel>/<messageId>", "gh:pr/1873"]
# type-specific fields
---
Body in Markdown with [[wikilinks]]. Relevant claims cite their source. ^[confluence:PROD/123456]
```

- **File name = title**; titles unique across the brain, no `\ / : * ? " < > | # ^ [ ]`.
- **Wikilinks** always to the canonical title; aliases resolved by the toolkit, flagged as non-canonical by validate.
- **External references** with prefixes: `jira:<KEY>`, `confluence:<SPACE>/<pageId>`, `teams:<team>/<channel>/<messageId>`, `gh:pr/<n>` / `gh:issue/<n>`, `figma:<fileKey>/<nodeId>`, `url:<url>`, `raw:<path>`.
- Implicit fields for every type: `type`, `title`, `aliases`, `created`, `updated`, `sources`.

### 3.3 Base preset `software-product`

| Area | Type | Folder | Key fields |
|---|---|---|---|
| functional | `feature` | `functional/features` | `status` (idea \| planned \| in-progress \| released \| deprecated), `jira: [EPIC-…]`, `modules: [[…]]`, `concepts: [[…]]`, `figma` |
| functional | `concept` | `functional/concepts` | `term_en`, `term_it`, `aliases`; body: definition, examples, "not to be confused with" |
| technical | `module` | `technical/modules` | `paths: [apps/billing/**]`, `owner_team` (free string), `interfaces: [[…]]`, `depends_on: [[module]]` |
| technical | `interface` | `technical/interfaces` | `kind` (rest \| event \| grpc \| lib \| ui-contract), `provided_by: [[module]]`, `consumed_by: [[module]]`, `spec_path` |
| technical | `environment` | `technical/environments` | `kind` (dev \| staging \| prod \| …), `url`; operational notes, **never secrets** |
| cross | `epic` | `epics` | `jira` (epic key, required), `status` (active \| done \| cancelled), `features: [[feature]]`, `modules: [[module]]`; body: goal / agreed scope / constraints and risks / discussion; budget 500 |
| cross | `decision` | `decisions` | `area` (functional \| ux \| technical), `status` (proposed \| accepted \| superseded), `date`, `supersedes: [[decision]]`, `affects: [[feature \| module \| interface]]`, `resolves: [[open-question]]`; body: context / options / outcome / consequences. No person names |
| cross | `open-question` | `open-questions` | `area`, `status` (open \| resolved \| dropped), `resolved_by: [[decision]]`, `affects` |

`decision` and `open-question` are **system types**: the toolkit relies on them. The init interview can extend any type but cannot remove system types.

**Epic vs feature.** Both stay in the preset, with separate roles. A `feature` is the product's behaviour as it is, or will be once released: it outlives any project. An `epic` is a change in delivery, tied to one Jira epic: it gathers what the team agreed about that change in Teams threads, Confluence analyses and meetings (scope, constraints, risks, pointers to the discussion) so that whoever builds it takes it into account. The rule that prevents overlap: anything that will still be true after the epic closes goes on feature, concept, module or decision pages, linked from the epic. When the Jira epic is done, the routine closes the page: it consolidates the lasting content into those pages and reduces the epic to a short outcome; closed epics leave the index after `archive_after_days`. Teams that do not plan in epics drop the type at init.

`module.paths` is the bridge between code and brain: given a set of changed files, the toolkit finds the modules, and from them interfaces, features and decisions.

### 3.4 Raw content and privacy

- **Teams messages and meeting transcripts:** never stored raw. Only synthesis in typed pages, citing a permalink.
- **Uploaded files (PDF, docx…):** extracted text saved as `brain/raw/YYYY/MM/<slug>.md` with `kind`, `captured`, `origin`, `link` (SharePoint/Confluence/Figma URL). Binaries are not committed; if no stable external link exists, `/pb:put` asks the user to upload the file somewhere and records the link.
- **Content rules** (in `AGENTS.md` and type prose): no judgements about people, no personal data, no customer personal data, no credentials.
- **`pb validate`** includes a secret-pattern check (tokens, keys, passwords, connection strings) that fails the PR.

### 3.5 Authority and conflicts

| Fact | Source of truth |
|---|---|
| Decisions, concepts, modules, interfaces, environments | The brain |
| Requirement detail (PRD on Confluence, acceptance criteria on Jira) | The external source; the brain summarises and links |

When ingestion finds a contradiction it **never overwrites silently**: it creates (or updates) an `open-question` citing both sources and links it from the affected pages.

### 3.6 Concision and size control

The brain is read by agents with a limited context window: every word must earn its place. Size is controlled at three points: what gets in, how it is written, and how it is maintained.

**Significance gate (ingestion).** Every skill that writes (`put`, `meeting`, `capture`, `sync`, routine) applies the same gate, defined once in `skills/_shared/` and in `AGENTS.md`. Content enters only if it is:
- **durable** — still true and useful in a month (not status updates, not who-is-doing-what-today);
- **non-derivable** — not obvious from the code, the diff, Jira fields or the linked document itself;
- **decision-relevant** — it changes how someone would build, test, design or explain the product.

What fails the gate is dropped (and, for the routine, listed in the digest as skipped).

**Writing rules.**
- **Update before create**: the LLM must look for an existing page (title, aliases, `resolve`) before creating one; a new page needs a reason that no existing page covers.
- **Consolidate, don't append**: knowledge pages are rewritten to stay a current, coherent description; no chronological logs, no "update of <date>" sections.
- **Link, don't copy**: external documents (PRD, Confluence analyses, Jira acceptance criteria, specs in the repo) are summarised in a few lines and linked, never transcribed.
- **One fact, one place**: a fact lives on its canonical page; other pages link to it.
- **Plain, dense prose**: no preambles, no restating the title, no filler; bullet points over paragraphs where possible.

**Budgets (toolkit-enforced).** Each type declares a soft word budget in its schema frontmatter (`max_words`), set by the init interview from preset defaults (indicative: concept 200, open-question 200, decision 400, environment 300, interface 400, feature 600, module 600). `pb validate` **warns** on pages over budget (it does not fail CI); the writing skill must then condense the page before committing. Extracted `raw/` text above a size threshold is not stored: a summary with the external link is kept instead.

**Maintenance.**
- `pb stats`: total pages and words per area/type, pages over budget, largest pages, growth since last run; reported in the routine digest.
- `/pb:lint` flags: pages over budget, near-duplicate pages (similar titles/aliases/content) to merge, resolved open questions and superseded decisions older than a threshold (to be archived out of `index.md`), orphan pages, stale content. `--fix` proposes merges and condensations with preview.
- Digests are rolling: `pb generate` keeps the last 30 days in `brain/digests/` (history remains in git).
- Context packs have a hard size cap; when exceeded, they include summaries and links instead of full pages.

## 4. Skills (MVP)

| Skill | Repo mode | Read mode | Purpose |
|---|---|---|---|
| `/pb:init` | ✅ | — | Grill-style interview + bootstrap; creates `brain/`, CI workflows, CLAUDE.md pointer |
| `/pb:put <input>` | ✅ | → explains channels | Ingest text, local files, Confluence pages, Jira issues/JQL, GitHub PRs/issues, Figma, URLs |
| `/pb:meeting [link\|today\|last]` | ✅ | — | Teams meeting (transcript, chat) → decisions, open questions, feature/concept updates. No raw |
| `/pb:capture` | ✅ | — | Dev-triggered analysis of the **current** session: distil decisions, module/interface findings, concepts, open questions; preview, then write |
| `/pb:fix <what is wrong>` | ✅ | — | Explicit correction of wrong information: find every page asserting it, correct it, record the correction |
| `/pb:sync [teams\|confluence\|github\|jira] [--check]` | ✅ | — | Incremental ingestion from configured sources using cursors in `.pb/state/` |
| `/pb:ask <question>` | ✅ | ✅ | Answer with citations to brain pages and sources; reads `index.md` first |
| `/pb:context <jira-key\|feature\|epic\|paths>` | ✅ | ✅ | Context pack for an agent or person: active epics, features, concepts, modules, interfaces, decisions, open questions |
| `/pb:lint [--fix]` | ✅ | — | Broken links, orphans, stale open questions, superseded-but-referenced decisions, modules whose `paths` no longer exist, contradictions |
| `/pb:schema [action]` | ✅ | — | Schema evolution: propose, apply with migration |
| `/pb:routine-setup` | ✅ | — | Configure and generate the nightly routine (see §6) |

All skills also trigger from natural language.

### 4.1 `/pb:init` — grill-style interview

Init does not ask the user to fill in a form. It runs a **grilling interview in rounds**, the same way the `grill-me` skill does:

1. **Gather facts first (no questions):** read the base preset; scan the monorepo — folder layout, workspace manifests, READMEs, existing ADRs, OpenAPI/AsyncAPI/proto specs, CODEOWNERS, CI config. Optionally look at a Confluence space and a list of Jira epics if the user names them.
2. **Build a design tree** of schema decisions (which types to keep/extend/add, folders, fields, enum values, module boundaries, glossary language, which sources to register).
3. **Ask the whole frontier per round**: every decision whose prerequisites are settled, numbered, each with a recommended answer derived from preset + scan, worded so "yes" accepts it.
4. **Recompute the frontier** after each answer; stop when no branch is open.
5. **Confirm** the full schema summary, then generate: `brain/schema/*`, `AGENTS.md`, empty folders, CI workflows, CLAUDE.md pointer.
6. **Bootstrap content:** propose initial `module` pages (with `paths` filled in), `interface` pages (from specs), `decision` pages (from existing ADRs), and optionally `feature`/`concept` seeds from Confluence/Jira — confirmed in bulk or one by one.

Facts are never asked of the user if they can be found in the repo or via connectors.

### 4.2 `/pb:context`

Given a Jira key (→ the epic page or features listing it, → features and modules), a feature or epic title, or a set of paths (→ modules via `paths` globs), returns a compact pack: relevant concepts with definitions, the feature(s), module(s) and interfaces, accepted decisions affecting them, open questions. Packs include the active epics that touch the features or modules in the pack, and the decisions and open questions affecting those epics. `pb-generate.yml` also pre-builds one pack per feature and per active epic in `brain/context/<title>.md` so agents can read it without the plugin.

### 4.3 `/pb:capture`

The developer triggers it, typically at the end of a working session, to analyse the **current** conversation (Claude Code; not available in read mode) and feed the brain.

1. Re-read the session: what was asked, what was explored, what was changed (files touched → modules via `paths`).
2. Extract only durable knowledge that passes the significance gate (§3.6): decisions taken (with alternatives considered and why they were discarded), discoveries about how modules and interfaces actually behave, new or clarified domain concepts, open questions left unresolved, wrong brain content discovered during the session (routed to the `/pb:fix` flow).
3. Discard everything session-specific: debugging steps, dead ends without a lesson, code that the diff already shows.
4. Show a preview: for each item, target page, create vs update, the exact lines added or changed.
5. Write after confirmation; commit on the current branch.

### 4.4 `/pb:fix`

Explicit correction when someone finds wrong information in the brain. Input: what is wrong, the correct information, and optionally the evidence (a file in the repo, a Jira issue, a Confluence page, "I verified it in code").

1. **Locate** every page that asserts the wrong fact: the page named by the user, plus a search across the brain for the same claim (titles, aliases, concepts, linked pages, generated context packs are rebuilt anyway).
2. **Classify** the error:
   - *misrecorded* — the brain never matched reality: correct in place;
   - *outdated* — it was true and changed: for a `decision`, never rewrite it; create a new decision that `supersedes` it; for knowledge pages, update the content;
   - *contested* — the evidence conflicts with an external source of truth (§3.5): do not pick a side, create an `open-question` citing both.
3. **Trace the origin**: check the `sources` of the wrong claim. If it came from an ingestion (Teams thread, Confluence page, PR), note it so the same claim is not re-ingested by the next sync (the sync state records corrected claims per source).
4. **Correct** with a preview, replacing the wrong statement (no "previously it said…" prose in the page body) and adding the evidence to `sources` as `fix:YYYY-MM-DD` plus the evidence reference.
5. **Log** the correction in `brain/.pb/corrections.md` (date, page, wrong → right, evidence) — append-only, used by `lint` to spot recurring error sources.
6. Commit on the current branch.

`/pb:capture` and `/pb:ask` hand off to this flow when they find a contradiction between the brain and the code or the conversation.

## 5. Agent-facing output

- **`brain/AGENTS.md`** — how to read the brain (start from `index.md`, use `glossary.md` for terminology, `context/` for feature and epic packs, `module.paths` to map code) and the rules for writing it.
- **Monorepo `CLAUDE.md` pointer** — added by init: "For product and domain context read `brain/AGENTS.md`."
- **`index.md`** — one line per page: type, title, one-line summary; grouped by area.
- **`glossary.md`** — bilingual table generated from `concept` pages.
- **`context/<feature or epic>.md`** — pre-built packs (§4.2).

## 6. Nightly routine

### Shape

- A **Claude Code cloud routine** (`/schedule`) on the monorepo, created by the **Engineering Manager**, who must be a member of every configured Teams channel and have read access to the configured Confluence spaces. Commits are attributed to that account.
- Runs nightly. Prompt generated by `/pb:routine-setup` from `templates/routine/`; it calls `/pb:sync teams confluence github jira`.
- **No PR.** Each run checks out the **target branch** configured at setup (`routine.branch` in `brain/schema/sources.md`), writes pages and the digest `brain/digests/YYYY-MM-DD.md`, runs `pb validate` (fix and repeat; on persistent failure it commits nothing and reports in the digest of the next run), then commits and pushes directly to that branch.
- The target branch is chosen by whoever sets up the routine:
  - `main` — knowledge lands immediately; the routine's account needs permission to push to `main` past branch protection (bypass for `brain/` or an exception in the ruleset);
  - a long-lived branch (e.g. `brain/inbox`) — no protection to bypass; someone merges it into `main` when they want, and that merge is the only review point.
- Before pushing, the routine rebases on the remote target branch; a conflict aborts the run without pushing and is recorded in the digest.

### Sources consumed

| Source | What | Incremental key |
|---|---|---|
| **Teams** | Configured teams/channels where the team (incl. non-devs) discusses | Per-channel cursor (last processed message time/id) |
| **Confluence** | Configured spaces or page trees where non-devs write analyses: **new and modified** pages | CQL `lastModified > cursor` per space; page version for re-ingest |
| **GitHub** | PRs merged since last run touching any `module.paths` | Merge time cursor |
| **Jira** | Epics of the configured projects: keeps `epic` pages aligned (status, goal) and closes them when done; features' Jira keys only on demand (`/pb:sync jira`) | `updated > cursor` per project |

### Teams triage

1. Group messages by **thread**; never ingest single messages out of context.
2. Defer threads still active (last reply < 24h) to the next run.
3. Classify each thread `ignore | signal | knowledge`. Only `knowledge` (decision, requirement clarification, domain explanation, incident learning, open question) creates or updates pages; `signal` is listed in the digest only.
4. Threads that mention an epic (Jira key, or the title/alias of an `epic` page) feed that epic page with delivery-specific content; lasting content goes to its own pages, linked from the epic.
5. The digest records what was ingested, what was skipped and why, making triage auditable.

### `/pb:routine-setup`

Interactive: lists teams/channels via the Microsoft 365 connector, Confluence spaces and Jira projects via Atlassian, lets the user pick; asks for the **target branch** (explaining the `main` vs long-lived branch trade-off and, for `main`, checking push permission); checks membership/access; writes the configuration into `brain/schema/sources.md`; generates the routine prompt and the `/schedule` instructions; documents owner and scope in `AGENTS.md`.

## 7. Distribution

- Plugin repo moved to the company GitHub org at first release, with `.claude-plugin/marketplace.json`.
- **Claude Code:** `/plugin marketplace add <org>/project-brain`, `/plugin install pb@project-brain`.
- **Cowork:** org admin syncs the marketplace repo (Organization settings → Plugins & skills), availability "Installed by default" for the product team. Members need the GitHub connector with read access to the monorepo.

## 8. Risks and verification spike (first task of the plan)

| # | Question | If it fails |
|---|---|---|
| S1 | Can the official GitHub connector in Cowork read `brain/` inside a large monorepo (subfolder selection, freshness, size limits)? | Fallback: a read-only Confluence mirror of `brain/` published by a GitHub Action (deferred phase) |
| S2 | Can the cloud routine push directly to the configured target branch (by default cloud sessions push to `claude/`-prefixed branches unless told otherwise), including `main` with a bypass for the routine's account? | Use a long-lived target branch instead of `main` |
| S3 | Does the Microsoft 365 connector read channel messages incrementally (pagination, since-date, thread replies)? | Use `chat_message_search` with date filters; reduce to fewer channels |
| S4 | Is Confluence CQL search by `lastModified` available through the Atlassian connector in routines? | Fall back to listing page trees and comparing versions |
| S5 | Is `python3` available in Cowork? | Not required: read mode only reads files |
